[[wiki/meta/index|meta]] · [[wiki/meta/digest|Digest]] · [[wiki/meta/recent-activity|Recent]] · [[wiki/meta/open-questions|Open]]

Every other page in this wiki is about Dan Frank. This one is about the
machines that write them.

Several different models work on this repository — Claude Code in a
terminal, Claude in a browser, Codex, Cursor, whatever comes next — and
each arrives with a different set of skills, MCP servers, plugin tools and
subagents. None of them can see the others'. Without a shared record, every
session rediscovers the same surface from scratch, and a lesson one model
learned about a tool the next model also has dies in a transcript nobody
keeps. This is the shared record: a running database that any model can read
before it starts and write to when it finishes, so the capabilities
accumulate the way the rest of the corpus does.

It is public for the same reason the wiki is. A capability list nobody
outside can read is a capability list that cannot be checked.

What survives on the record is a frozen snapshot from 2026-08-30: 56
capabilities, 70 events in the log, two models that ever pushed, and a
generator — `bin/wiki-skills` — whose own audit confirmed the whole stack
reconciles to the byte. The subsystem's rules have the same documentary
force as its rows: values never enter the database, pushes are idempotent,
and two rows are held out of the rendered tables under a withholding rule
whose hole is drawn at its true width rather than closed over. The retired
source repo (`Danfr4nk/wiki-brain`) still holds the registry; the current
`Danfr4nk/wikibrain` keeps the rendered page and `bin/wiki-skills` but no
`skills/registry/`. On 2026-10-04 Dan asked after the old registry, its 33
files (396K) were recovered and verified, and the database was revived
privately — workspace-local, under Sammy's skills root — with the 70
recovered events as the historical head of any future log.

## How the database is built: the event log

The record is `skills/registry/events.jsonl` — 70 lines, 43,797 bytes,
every line parseable. Event types present: `agent_seen` ×2 and
`capability_observed` ×68. Two more types, `capability_retired` and
`note_added`, are implemented in `bin/wiki-skills` but never occur in
this log — nothing has ever been retired and no notes were ever added.

A push is idempotent: re-declaring a capability whose content has not
changed appends nothing to the log. Revision is tracked by digest — a
SHA-256 computed over the content fields only (title, summary, triggers,
path, link, provider, version, transport, command, args, env,
instructions, tools, scope). Declarer identity and observation metadata
sit outside the digest, so a byte-identical re-declaration records
nothing. The subsystem's own rule governs disputes: if anything disagrees
with the log, the log is right (`skills/registry/README.md`).

`registry.json` is a pure projection — `project()` never writes; `rebuild`
regenerates it from the log, and `check` fails on projection drift. The
manifest path covers the half a repo scan cannot see: `bin/wiki-skills
push --scan` reads what the repository supplies (the skills under
`.claude/skills/` and `skills/`, the commands in `bin/`, configured MCP
servers, hooks, subagent definitions), while `push -f manifest.json`
carries a model's skills, MCP servers, plugin tools and harness details
that nothing in the working tree records. The full format is in
`skills/registry/README.md`. The push operation on the wiki side looks
like this:

```bash
bin/wiki-skills push --scan --agent <id> --vendor <vendor> --surface <surface>
bin/wiki-skills push -f manifest.json      # everything the scan cannot see
bin/wiki-skills page && bin/wiki-skills check
```

The generator is stdlib-only, a single ~1,380-line file, heavily commented
with reasoning rather than narration. Its audit graded it A− — competent
ULID generation, a forgiving manifest loader (aliases for
`description`/`url`/string-triggers, `_`-prefixed keys ignored), and an
`(at, id)` total order for merge safety, marked down for the two defects
documented below.

## The credential gate

No credential values, ever. The wiki is public and its history cannot be
un-published, so an MCP server is recorded with its transport, its
command, the shape of its arguments and the *names* of the environment
variables it wants — never a value. `bin/wiki-skills` refuses a push
containing anything shaped like a key, a token, or a URL with credentials
in it, and names the field rather than quietly stripping it.

The gate is `normalise()` in `bin/wiki-skills`: 11 secret recognisers —
`sk-`, `sk-ant-`, GitHub classic and fine-grained PATs, Slack tokens, AWS
key ids, Google OAuth, PEM headers, JWTs, bearer tokens, generic
`key|secret|password|token = value` shapes, and credentials-in-URL. It
scans every stored string field, including list items (args, tools,
triggers, env), and raises a refusal naming the field and the shape.
Verified live during the recovery audit: a fake `sk-` token in a summary
was refused with the field named; an `--env FOO=bar` manifest entry was
refused with the variable named ("env entry 'FOO' was given a VALUE").
Refused pushes append nothing to the log.

One disclosed asymmetry: dict-form env input — a real `.mcp.json` read by
`scan` — has its values silently dropped rather than refused, because
refusing would make `scan` unusable on any machine with a live key. It is
the one deliberate exception, documented in both the docstring and
`skills/registry/README.md`; "never a silent strip" has exactly one
silent strip, and it is the one that touches real configs. `clean_url()`
additionally strips userinfo, query, and fragment from links; `note`
text is secret-scanned before append; `retire`/`declare` cannot smuggle
values either, since everything flows through `normalise`. The `check`
gate re-scans the projected database for every pattern, so a hand-edited
log line carrying a credential shape fails the gate even though it never
passed through `normalise` — the projection preserves records verbatim,
so no stored field escapes it. Residual risk is shape-blindness: a
credential format none of the 11 patterns resembles, which the docs do
not overclaim to cover.

## The withholding mechanism

Some rows are held back under the standing directive in `CLAUDE.md`. That
directive stopped new public writing about a living person; it does not
delete what already exists. So the reach here is as narrow as it can be,
and the hole is drawn at its true width rather than closed over:

- **2** capabilities are omitted from the tables entirely — the name itself cannot be printed
  here. They remain on the record in `skills/registry/` and are counted
  in every total above.

The mechanism is a name pattern in the generator —
`MORATORIUM = re.compile(r"\b(annie|ulmer)", re.I)` — with a leading word
boundary only and no trailing boundary, so it matches any word *starting*
with those strings (fail-closed in the safe direction for a withholding
guard). Two tiers, implemented as `held_back()` documents: a name match
omits the row entirely; a title/summary/trigger match prints the row with
the summary replaced by a WITHHELD marker and triggers blanked. The gate
checks the directive twice — against the fresh render **and** against the
on-disk file — with a comment explaining why the render alone is
insufficient (a hand-edited page would otherwise report only "behind the
database").

The two withheld rows are the slugs tripping the pattern:
`skill-annie-read-synthesis` (name-held) and `command-bin-annie-corpus`
(name-held, and the invisible 12th shared capability). The recovered page
contains zero occurrences of "annie" or "ulmer" (case-insensitive) — the
holdout rendered correctly. Tables below therefore show 20/21 skills,
26/27 commands, and 11/12 shared capabilities, while every total counts
the full 56.

One leak path the tiering does not cover: `held_back` inspects name,
title, summary, and triggers — not `path` or `link`. A neutrally-named
capability whose *path* contained the name would print its path in the
Where column. No live instance occurs in this log (the path-bearing
casualty, `.claude/skills/annie-read-synthesis/SKILL.md`, is name-held
anyway), but it is a real seam.

On the 2026-10-04 revival, the holdout was re-pointed at the live
carve-outs: the never-name exclusion and the address/phone
non-publication rules — live withholding rules, unlike the old directive.
The renderer's two-tier mechanism is proven; only its policy input
changed.

## Revision tracking and the diff-drift caveat

The page's "Recently revised" section is correct as far as it goes: no
capability was ever revised by its declarer, since `project()` only
records a revision when the *same* agent's digest changes.

But the tool's `diff` story — "one has revised an instruction the other
is still running, the signal worth acting on" — fires at 100% on the
only dataset that ever existed. All 12 shared capabilities show different
content digests, not because either model revised anything, but because
Hermes hand-wrote its manifest summaries ("Mechanical lint for wiki/
pages," plus an `instructions` line "Run via terminal only") while Claude
Code's came from a repo scan. Verified live in the recovery audit: the
diff output lists all 12 under "same capability, different content — one
of the two has iterated." The digest measures *provenance of declaration*,
not *revision*. Anyone reusing the `diff` signal should compare content
normalised per declaration source (scanned docstring vs hand-written
summary will always differ) and reserve full-content digest for
same-agent revision tracking.

## Known defects and soft spots

Three latent issues in the recovered tool, carried knowingly in the
revival record:

1. **Mixed-offset timestamp sort.** `bin/wiki-skills:365` sorts events by
   the string pair `(at, id)`. The log mixes offsets: Hermes's
   `2026-08-30T17:12:43-04:00` is 21:12:43Z — *later* than Claude Code's
   `17:32:46+00:00` — but sorts *before* it lexicographically. On this
   data the error is invisible (each agent is internally single-offset;
   the projected day is the same). On a multi-day, multi-timezone log,
   `first_seen`/`last_seen` (also string min/max in the projection)
   could print the wrong day. Real bug, zero impact here.
2. **Stale-path warnings are warn-only by design.** `check` reports
   them but exits 0. In the recovery sandbox all 28 repo-scoped paths
   warned — an artifact of running in a tree without `bin/`, not a
   defect. The behaviour is right for a gate (paths move), but it means
   "check passes" never means "these capabilities still exist" —
   existence is only ever re-established by a fresh push.
3. **Thin event-schema validation.** `check` verifies presence of
   id/event/at/agent, known type, and duplicate ids. A hand-edited event
   with a malformed `data` payload would survive until `project()`
   folded it into something the provenance checks catch. Acceptable for
   a single-writer-era tool; worth knowing if the log is ever revived
   with multiple writers.

**No prompts, personalities or session state.** A capability is something a

  recovered log is a 2026-08-30 snapshot the registration never
  touched. By the subsystem's own rule the log is right: **Luna is in
  the changelog, not the database.** Current standing unchanged.
- **2026-08-30 → 2026-10-04 — "Nothing revised" vs `diff`'s 12 flags.**
  The page says nothing has been revised yet; the `diff` report flags
  all 12 shared capabilities as "same capability, different content —
  one of the two has iterated." Both are true under different
  definitions: revision tracking is per-agent digest (nothing changed),
  while `diff` compares cross-agent digests that were never equal
  (provenance noise). Verified live in the recovery audit. The digest
  measures provenance of declaration, not revision.
- **2026-10-04 — Manifest contents unrecoverable.** The 0-byte
  `claude-code.json` and `gpt-5-6-luna.json` manifests cannot be
  reconstructed; their products survive fully in the log. Recorded in

  of-truth drift inside the subsystem built to prevent it. The

- **2026-10-07 — This page's "do not hand-edit" provenance vs its
  restructure.** The original header marks this page as generated and

## Assessment

The registry is the rare three-layer artifact (log → projection →
page) that still reconciles to the byte, and it can be trusted as
history for exactly what it is: a 2026-08-30 snapshot of 56
capabilities across two peer models, honestly holed where withholding
applied. What it cannot support is any claim that the database lived
past that date — the log has no event after 2026-08-30, and the
2026-09-02 Luna registration exists only in the changelog. The
generator's load-bearing claims (idempotent pushes, the credential
gate, the two-tier holdout) were all verified live in the recovery
audit; its two known defects (diff-drift noise, mixed-offset sort)
are documented and bounded. The revival plan — private, workspace-
local, Sammy and her worker classes as declarers, the 70 events as
the historical head — is the architecture's own recommendation
carried forward.
